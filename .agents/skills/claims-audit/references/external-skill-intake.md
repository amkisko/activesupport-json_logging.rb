# External skill intake

Use when researching a public skill, prompt pack, or agent tool for possible addition to a prayers catalog. Prefer one live-work note per candidate over many parallel orphan chats.

## Fit

1. Name the user problem the material claims to solve.
2. Check whether an existing prayer already covers it (fragment, skill, or reference). Prefer update over a new package.
3. Confirm the material is generic guidance. Reject project URLs, live secrets, client names, and deployment-specific commands.

## Evidence

1. Run this claims-audit skill for material external claims, versions, and citations.
2. Prefer primary sources (RFC, upstream repo file, official docs) over scanner scores or marketing pages.
3. Record supported, partial, unsupported, outdated, contested, or unverifiable outcomes. A link alone is not support.

## House rules

1. Follow writing-prose: plain prose, keyboard-accessible ASCII for structure, no markdown tables or bold in prayer bodies.
2. Follow docs-conventions for any durable note under `docs/`.
3. Follow dependency-policy and minimal-implementation before adding a package or dependency.
4. Prefer instrument vocabulary (check-in, probe, monitor) over body metaphors.

## License and duplication

1. Confirm the upstream license allows reuse of what you would copy or adapt.
2. Do not vendor a readiness score or scanner as a house pass/fail.
3. If the useful residue is a checklist, put it in an existing skill reference or a stable docs guide rather than a near-duplicate package.

## Record

Write one `docs/issues` note for the candidate (or for a small batch that shares one decision). Link the upstream URL and the prayer packages that would change. Implement only after that note states the decision.
